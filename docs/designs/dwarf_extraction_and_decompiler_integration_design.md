# Backend-Neutral DWARF Extraction & Decompiler Integration (`twdll-dwarf` -> SQLite -> Ghidra / IDA)

*   **Author:** Bukowa
*   **Status:** Proposed
*   **Date:** 2026-11-25

--------------------------------------------------------------------------------

## Overview

This design decouples DWARF v4 debug extraction from any single decompiler backend so `twdll` will extract the targeted C++ DWARF subset from `attila_linux_64` out-of-process via a standalone Rust binary (`twdll-dwarf`, built on `gimli v0.34.0`, `object v0.40.0`, `memmap2 v0.9.12`, `fnv v1.0.7`, and `libc v0.2.191` `libsqlite3` C FFI). Both **Ghidra 12.2** (now) and **IDA 9.5** (later) consume the resulting backend-neutral SQLite tables inside `.twdll/extract/<decompiler>_attila_linux_64.sqlite`.

During `twdll analyze` on `attila_linux_64`, `twdll` will disable Ghidra's built-in `DWARF` analyzer so headless analysis completes within default JVM heap limits on 8 GiB hosts. During `twdll extract`, `twdll.database` will initialize `.twdll/extract/<decompiler>_attila_linux_64.sqlite.staging` with the SQLite schema, invoke `twdll-dwarf` to bulk-insert the deduplicated `dwarf_*` tables (types, pre-flattened struct layouts, synthesized vtable slot tables, function signatures, entry-PC parameter registers, local variable live ranges, and inlined call sites), and stream pass-scoped batches into Ghidra's `ProgramDB` before running `DecompInterface` to produce typed C++ pseudocode.

## Background & Terminology

*   **Reference binary (`attila_linux_64`)**: The 723.8 MiB 64-bit Linux ELF binary for Total War: Attila (`image_base = 0x400000`), containing 469 DWARF v4 Compilation Units (CUs) compiled with Clang 3.4.2 (236 CUs) and GCC 4.8.1/4.8.2 (233 CUs), 313,972 `.symtab` entries (including `11,857` `_ZTV*` C++ vtable symbols), and ~624 MiB of `.debug_*` sections (`.debug_info` 242.78 MiB across `23,553,961` Debugging Information Entries (DIEs), `.debug_str` 123.85 MiB, `.debug_pubnames` 86.94 MiB, `.debug_loc` 85.92 MiB, `.debug_pubtypes` 30.21 MiB, `.debug_ranges` 30.14 MiB, `.debug_line` 21.30 MiB). It serves as the reference anchor for mapping stripped 32-bit Windows PE DLLs (`attila_windows_32.dll`, `rome2_windows_32.dll`, `tob_windows_32.dll`).
*   **`Slice 3` & `Step 3A` empirical gate**: In [SPEC.md §6.3](../../SPEC.md#L229-L235), `Slice 3` is the pipeline implementation phase covering `twdll extract` and `twdll sql`, and `Step 3A` is its pre-implementation empirical verification gate where DWARF extraction, decompiler API outputs, peak JVM + native `decompile` RSS, and bulk C++ pseudocode throughput are measured on `attila_linux_64` before locking decompiler-extracted SQLite table columns.
*   **`twdll-dwarf` (`gimli v0.34.0` + `object v0.40.0` + `memmap2 v0.9.12` + `fnv v1.0.7` + `libc v0.2.191` `libsqlite3` FFI)**: A standalone Rust CLI binary at `tools/twdll-dwarf/` (built locally via `cargo build --release --manifest-path tools/twdll-dwarf/Cargo.toml` or staged under `.twdll/init/tools/twdll-dwarf/`). Benchmarked on all 469 CUs (`23,553,961` DIEs) of `attila_linux_64` at `52.04s` wall time and `2.11 GiB` peak RSS (including the `723.8 MiB` ELF `mmap`), `twdll-dwarf` performs cross-CU type deduplication, struct layout flattening, vtable slot synthesis, and single-transaction `libsqlite3` prepared-statement bulk insertion well within the under 60s and under 3.2 GiB peak RSS budget.
*   **Global cross-CU type deduplication & STL stubbing**: Because `attila_linux_64` has no `.debug_types` section and zero `DW_FORM_ref_addr` cross-CU references, its 469 CUs re-emit `534,600` raw struct/class/enum/union DIEs (`383,609` definitions and `150,991` `DW_AT_declaration` forward declarations). Deduplicating named types by canonical qualified name (`namespace_chain::TypeName`) and scoping anonymous or function-local types by `(unit_id, die_offset)` collapses the named types to `116,169` unique named types (`101,264` with full definitions, `14,905` declaration-only). Standard library and compiler-internal template implementation structures (`std::_Rb_tree*`, `std::__detail::*`, `__gnu_cxx::*`) are flagged as opaque sized stubs (`byte_size >= 1`) after evaluating their C++ calling-convention non-triviality so decompiler type injection avoids importing unreferenced STL template instantiation trees.
*   **Pre-flattened Itanium C++ struct layouts**: Under the x86-64 Itanium C++ ABI, `attila_linux_64` contains `3,641` classes using empty-base-optimization (EBO, where a 1-byte empty base overlaps a data member or sibling base at the same `byte_offset`), `213` classes packing derived fields into a base class's trailing padding (`base.byte_offset < member.byte_offset < base.byte_offset + base.byte_size`), and `791` virtual base inheritances (`DW_AT_virtuality = 1` with dynamic vtable-offset `DW_FORM_exprloc` expressions). `twdll-dwarf` resolves non-virtual members and bases into disjoint `[byte_offset, byte_offset + byte_size)` layout intervals in SQLite while recording `vbase_vtable_offset` (`byte_offset = NULL`) on virtual bases (`is_virtual = 1`), which are excluded from static `StructureDataType` offset placement.
*   **Hidden structure-return pointer (`sret`)**: Under the System V x86-64 and Itanium C++ ABIs, functions returning structs `> 16` bytes or non-trivial-for-calls C++ classes `<= 16` bytes (any class with a virtual method, non-trivial destructor, user-declared copy/move constructor, or non-trivial base/member) pass a hidden return-storage pointer in `RDI` (`DW_OP_reg5`), shifting the implicit `this` pointer on member functions from `RDI` to `RSI` (`DW_OP_reg4`) (or shifting the first user integer argument on free functions from `RDI` to `RSI`). Across `143,602` out-of-line C++ methods with formal parameters in `attila_linux_64`, `9,407` methods shift `this` to `RSI` due to `sret`.

## The Problem

1. **Ghidra 12.2's built-in `DWARFAnalyzer` exhausts JVM heap on 8 GiB hosts**: In Ghidra 12.2 (`DWARFAnalyzer.added()` -> `DWARFProgram.init()` -> `DIEContainer.indexData()`), Ghidra indexes all `23,553,961` DIEs before checking `DWARFImportOptions`. Its `indexDIEATypeRefs()` pass inserts every `DW_AT_type` edge across all 469 CUs into a boxed `ArrayListValuedHashMap<Long, Long>`, exhausting `pyghidra.start()`'s default ergonomic JVM heap (~1.9 GiB on an 8 GiB machine) even when `Import Data Types` and `Create Function Signatures` are disabled.
2. **Ghidra 12.2's built-in DWARF importer contains five C++ defects even when given unlimited RAM**:
    *   **Unimplemented C++ vtables**: Ghidra's `DWARFAttributeId` defines `DW_AT_virtuality` and `DW_AT_vtable_elem_location`, but neither attribute is read anywhere in Ghidra's DWARF importer (`DWARFDataTypeImporter.populateStubStruct()` ignores `DW_TAG_subprogram` children of classes). As a result, `_vptr$` fields remain untyped `int **` pointers and all virtual calls decompile as raw pointer arithmetic `(**(code **)(*(long *)this + 0x28))(this, ...)`.
    *   **Dropped `this` pointer on Linux x86-64**: `ThisCallingConventionDWARFFunctionFixup` assigns `"__thiscall"` to C++ member functions on `x86-64-gcc.cspec`, which defines no `__thiscall` prototype model. Whenever a function falls back to formal signature commitment (`DYNAMIC_STORAGE_ALL_PARAMS`), `FunctionVariables.removeExplicitThisParameter()` deletes the explicit `this` parameter and falls back to `__stdcall`, dropping `this` and shifting all parameters left by one register.
    *   **Broken `sret` parameter storage (`9,407` methods in `attila_linux_64`)**: `x86-64-gcc.cspec` classifies `<= 16`-byte structs strictly by byte size (`RAX`/`RDX` return), ignoring C++ non-trivial destructors and copy/move constructors (`3,513` dtor/virtual returns and `1,247` user-copy-ctor returns `<= 16` bytes in `attila_linux_64`). Moreover, `DWARFFunction.updateFunctionSignature()` clears `autoParams = null` whenever `CUSTOM_STORAGE` is used, dropping the auto-generated `__return_storage_ptr__` parameter.
    *   **Itanium EBO, tail-padding, and virtual-base layout collisions**: `DWARFDataTypeImporter` drops empty bases (`3,641` classes), fails packing or drops base subobjects on tail-padding reuse (`213` classes), and cannot represent dynamic vtable-offset virtual bases (`791` inheritances).
    *   **Dropped `-O2` local variables and hidden inline calls**: `DWARFVariable.readLocalVariableStorage()` queries `.debug_loc` only at the function entry address (`dfunc.getEntryPc()`), returning `null` for `-O2` locals whose live ranges begin after the prologue, while `DWARFImportOptions.outputInlineFuncComments` defaults to `false`.
3. **Black-box `ddbug_parser v0.6.0` and pure-Python `pyelftools` cannot satisfy these C++ requirements alone**: `pyelftools 0.33` takes 53.66s and 3.56 GiB RSS for just 10 of 469 CUs (~41.2 minutes projected). Meanwhile, `ddbug_parser v0.6.0` keeps its underlying `gimli` handles private (`pub(crate)`) and drops `DW_AT_virtuality`, `DW_AT_vtable_elem_location`, `DW_AT_containing_type`, `DW_AT_artificial`, `DW_AT_object_pointer`, virtual-base `exprloc` flags (silently defaulting failed virtual-base offsets to `0`), and `DW_AT_specification` parameter inheritance across `2,268` out-of-line methods.
4. **DWARF extraction and storage must remain backend-neutral**: Coupling DWARF tables to Ghidra internals or introducing a separate `.sqlite` file outside `.twdll/extract/<decompiler>_<binary>.sqlite` would break `twdll sql` attachment ([SPEC.md §6.4](../../SPEC.md#L241-L245)) and force schema rework when IDA 9.5 support is added.

## Goals

*   **Single per-binary SQLite database with backend-neutral `dwarf_*` tables**: Store both `dwarf_*` tables and decompiler-extracted tables inside `.twdll/extract/<decompiler>_attila_linux_64.sqlite`, with `twdll.database` owning all SQLite DDL, `.sqlite.staging` creation, `WAL` checkpointing, and final `meta` (`completed`, `binary_sha256`, `image_base`) atomic completion.
*   **Targeted C++ DWARF v4 extraction via `twdll-dwarf` (`gimli` + `object` + `libsqlite3` FFI)**: Extract and globally deduplicate types, pre-flattened struct layouts (resolving EBO, tail-padding, and virtual bases), synthesized vtable slot tables (`DW_AT_vtable_elem_location` + inherited base slots + `.symtab` `_ZTV*` `D1Ev`/`D0Ev` entries), function signatures (with `DW_AT_specification` parameter inheritance and `sret` detection), entry-PC parameter registers and entry-`RSP`-normalized stack offsets, `.debug_loc` local variable live ranges, and `DW_TAG_inlined_subroutine` ranges in under 60s and under 3.2 GiB peak RSS (benchmarked at `52.04s` and `2.11 GiB` peak RSS).
*   **Low-RAM Ghidra `analyze` on `attila_linux_64`**: Disable Ghidra's `"DWARF"` analyzer inside an open program transaction before running `pyghidra.analyze(...)` on `BinaryArch.ELF64` targets, and stage temporary Ghidra projects under `/var/tmp` on Linux (avoiding `/tmp` `tmpfs` RAM exhaustion while keeping paths dot-free).
*   **Extract-time pass-scoped batch population for typed C++ pseudocode**: At the start of `twdll extract` on `attila_linux_64`, stream four pass-scoped SQLite queries into the temp-staged Ghidra `ProgramDB` across four coarse transactions (clearing undo history after each) with conflict-free `StructureDataType` layouts (for referenced non-stubbed types), `<Class>_vtbl` vtable structs, `FunctionUpdateType.CUSTOM_STORAGE` parameter/return storage bindings, `LocalSymbolMap` stack/register locals, and `CommentType.PRE` inlined call annotations before running `DecompInterface`.
*   **Zero `twdll.toml` or CLI flag expansion**: Resolve `twdll-dwarf` deterministically without relying on user `PATH` and without adding new keys to `twdll.toml` `[toolchain]` or new root CLI flags.

## Non-Goals

*   **Forking or patching Ghidra 12.2's Java `DWARFAnalyzer` JARs**: All DWARF parsing happens out-of-process in `twdll-dwarf`, and all Ghidra `ProgramDB` population happens via `pyghidra` in `twdll._ghidra`.
*   **Implementing IDA 9.5 in this design**: IDA 9.5 remains deferred until Windows host testing; this design defines the backend-neutral `dwarf_*` SQLite schema so IDA 9.5 can query the exact same tables later.
*   **Mutating `.twdll/analyze/ghidra_attila_linux_64.gpr` during `twdll extract`**: All type, vtable, signature, local, and comment mutations during `twdll extract` execute against the temporary disk-staged project copy and are discarded on close so `.twdll/analyze/` artifacts remain immutable.
*   **Stage 3 C++ SDK (`src/`, `build`/`test`/`pack`/`install`)**: Frozen and out of scope.

## Technical Plan (Architecture)

### 1. Backend-Neutral DWARF & Decompiler Data Flow

`twdll analyze` produces the base `.gpr`/`.rep/` project with `DWARF=off`. During `twdll extract`, `twdll.database` creates `.twdll/extract/<decompiler>_attila_linux_64.sqlite.staging` with the full DDL, `twdll-dwarf` bulk-inserts the deduplicated `dwarf_*` rows via `libsqlite3` prepared statements, and `twdll._ghidra` streams four pass-scoped batches from those `dwarf_*` tables into the temp-staged `ProgramDB` before extracting decompiler facts and C++ pseudocode into the same staging database:

```text
  attila_linux_64 (ELF64 + DWARF v4 + .symtab _ZTV)
          |
          +---> [ twdll analyze ] (Ghidra: Analyzers.DWARF = false,
          |       /var/tmp staging on Linux, ELF + .symtab + demangler + xrefs)
          |               |
          |               v
          |     .twdll/analyze/ghidra_attila_linux_64.gpr|.rep + .meta.json
          |               |
          v               | (staged to /var/tmp on Linux during extract)
  [ twdll extract ]       |
    1. twdll.database initializes ghidra_attila_linux_64.sqlite.staging (DDL)
    2. twdll-dwarf (Rust: gimli + object + libsqlite3 FFI) bulk-inserts dwarf_* tables
    3. twdll._ghidra streams 4 pass-scoped SQLite queries into temp ProgramDB:
         - Pass 1: Enums, typedefs, and sized struct/union shells (STL stubbed)
         - Pass 2: <Class>_vtbl structs + pre-flattened referenced struct members
         - Pass 3: CUSTOM_STORAGE signatures (explicit RDI sret + RSI this)
         - Pass 4: Stack & multi-range register locals + CommentType.PRE inlines
    4. twdll._ghidra extracts functions, symbols, strings, xrefs, sections,
       and typed DecompInterface C++ pseudocode into .sqlite.staging
    5. twdll.database checkpoints WAL, switches journal_mode = DELETE, writes
       meta (completed, binary_sha256, image_base), and renames to .sqlite
                          |
                          v
                  [ twdll sql ] (attaches ghidra_attila_linux_64.sqlite
                                 as read-only schema alias attila_linux_64)
```

### 2. DWARF SQLite Data Model (Backend-Neutral)

All 10 `dwarf_*` tables reside in `.twdll/extract/<decompiler>_attila_linux_64.sqlite` alongside `meta` and the decompiler-extracted tables (`functions`, `symbols`, `strings`, `types`, `xrefs`, `sections`). Virtual addresses are stored as plain integers normalized to the ELF64 `PT_LOAD` virtual base (`image_base = 0x400000`, recorded in `meta` and verified against `program.getImageBase()`), with zero Ghidra-specific identifiers:

*   **`dwarf_units`**: `unit_id` (`INTEGER PRIMARY KEY`), `name` (`TEXT`), `comp_dir` (`TEXT`), `producer` (`TEXT`), and `language` (`INTEGER`) across all 469 compilation units.
*   **`dwarf_types`**: Globally deduplicated canonical types keyed by `type_id` (`INTEGER PRIMARY KEY`), with `kind` (`TEXT`: `primitive`, `struct`, `class`, `union`, `enum`, `typedef`, `pointer`, `reference`, `rvalue_reference`, `array`, `subroutine`, `ptr_to_member`, `const`, `volatile`), `qualified_name` (`TEXT`, scoped by `(unit_id, die_offset)` for anonymous or function-local types), `byte_size` (`INTEGER`, nullable for incomplete types), `target_type_id` (`INTEGER`, nullable; for pointers/references/typedefs/modifiers/arrays), `array_count` (`INTEGER`, nullable; total element count from `DW_TAG_subrange_type` for `kind = 'array'`), `containing_type_id` (`INTEGER`, nullable; primary vtable owner from `DW_AT_containing_type` or `ptr_to_member` class type), `vtable_symbol` (`TEXT`, nullable; matched `.symtab` `_ZTV*` symbol name via Itanium demangled class name), `vtable_address` (`INTEGER`, nullable; integer address of primary `_ZTV + 0x10` slot 0), `is_declaration` (`INTEGER`: `0` or `1`), `is_non_trivial_for_calls` (`INTEGER`: `1` if `byte_size > 16` or has virtual methods, non-trivial destructor, user-declared non-defaulted copy/move constructor, or non-trivial base/member, evaluated before `is_stl_stub`), `is_stl_stub` (`INTEGER`: `1` for internal `std::_Rb_tree*`, `std::__detail::*`, `__gnu_cxx::*` template types stubbed during decompiler injection), and `is_referenced` (`INTEGER`: `1` when transitively referenced by concrete `dwarf_functions`, `dwarf_parameters`, `dwarf_vtable_entries`, or `dwarf_variables`).
*   **`dwarf_members`**: Pre-flattened struct/class/union layout components keyed by `member_id` (`INTEGER PRIMARY KEY`), with `parent_type_id` (`INTEGER`, indexed), `ordinal` (`INTEGER`), `name` (`TEXT`), `member_type_id` (`INTEGER`), `byte_offset` (`INTEGER`), `byte_size` (`INTEGER`), `bit_offset` (`INTEGER`, nullable), `bit_size` (`INTEGER`, nullable), `is_artificial` (`INTEGER`: `1` for `_vptr$...`), `is_flattened_base_member` (`INTEGER`: `1` when promoted from a base class whose tail/interior padding was reused by a derived member), and `is_layout_conflict` (`INTEGER`: `1` for overlapping anonymous-union secondary arms or sub-byte bitfields skipped during flat struct component population).
*   **`dwarf_inheritance`**: `inheritance_id` (`INTEGER PRIMARY KEY`), `derived_type_id` (`INTEGER`, indexed), `base_type_id` (`INTEGER`), `byte_offset` (`INTEGER`, nullable when `is_virtual = 1`), `vbase_vtable_offset` (`INTEGER`, nullable; parsed from virtual-base `DW_FORM_exprloc`), `is_virtual` (`INTEGER`: `0` or `1` from `DW_AT_virtuality`), `is_empty_base` (`INTEGER`: `1` for 1-byte empty bases overlapping any member or sibling base at the same `byte_offset`), and `has_tail_padding_overlap` (`INTEGER`: `1` when derived members occupy the base's trailing padding).
*   **`dwarf_vtable_entries`**: Synthesized vtable slot layout keyed by `PRIMARY KEY (class_type_id, slot_index)`, with `method_name` (`TEXT`), `linkage_name` (`TEXT`, nullable), `function_id` (`INTEGER`, nullable for pure virtuals or external targets), `target_address` (`INTEGER`, nullable; resolved from the primary `_ZTV + (2 + slot_index) * 8` array in `.rodata` / `.data.rel.ro`), and `is_pure_virtual` (`INTEGER`: `0` or `1`, set when `virtuality = 2` or `target_address` points to `__cxa_pure_virtual`). Populated by merging inherited base vtable slots with in-class `DW_AT_vtable_elem_location` declarations and the primary `_ZTV*` function-pointer table so both complete (`D1Ev` at slot `k`) and deleting (`D0Ev` at slot `k + 1`) virtual destructor slots are included.
*   **`dwarf_enumerators`**: `PRIMARY KEY (enum_type_id, ordinal)`, with `name` (`TEXT`) and `value` (`INTEGER`).
*   **`dwarf_functions`**: `function_id` (`INTEGER PRIMARY KEY`), `unit_id` (`INTEGER`), `address` (`INTEGER`, nullable for uninstantiated inline-only declarations; indexed for joining against decompiler `functions.address` and `symbols.address`), `byte_size` (`INTEGER`, nullable), `linkage_name` (`TEXT`, nullable; from `DW_AT_linkage_name` or Clang `DW_AT_MIPS_linkage_name`, indexed for fallback joins), `qualified_name` (`TEXT`), `containing_type_id` (`INTEGER`, nullable), `return_type_id` (`INTEGER`, nullable), `vtable_slot_index` (`INTEGER`, nullable; from in-class `DW_AT_vtable_elem_location`), `virtuality` (`INTEGER`: `0` none, `1` virtual, `2` pure virtual), `is_inline` (`INTEGER`: `0` or `1`), `is_declaration` (`INTEGER`: `0` or `1`), `is_variadic` (`INTEGER`: `1` when `DW_TAG_unspecified_parameters` child is present), `has_object_pointer` (`INTEGER`: `1` if C++ non-static method via `DW_AT_object_pointer` or artificial param 0 `this`), `is_sret` (`INTEGER`: `1` when hidden return pointer occupies `RDI`), `decl_file` (`TEXT`, nullable), and `decl_line` (`INTEGER`, nullable).
*   **`dwarf_parameters`**: Formal parameters (merged across out-of-line definition and in-class `DW_AT_specification` declaration so the `2,268` parameter-omitting out-of-line methods retain full parameter lists) keyed by `PRIMARY KEY (function_id, ordinal)`, with `name` (`TEXT`, nullable), `type_id` (`INTEGER`), `is_artificial` (`INTEGER`: `1` for `DW_AT_artificial` `this`), `is_object_pointer` (`INTEGER`: `0` or `1`), `storage_kind` (`TEXT`: `register`, `stack`, `none`), `dwarf_reg` (`INTEGER`, nullable; entry-PC DWARF register number: `5` = `RDI`, `4` = `RSI`, `1` = `RDX`, `2` = `RCX`, `8` = `R8`, `9` = `R9`, `17..24` = `XMM0..XMM7`), `reg_name` (`TEXT`, nullable; Ghidra register name `"RDI"`, `"RSI"`, etc.), and `stack_offset` (`INTEGER`, nullable; normalized to entry-PC `RSP` via `DW_AT_frame_base`).
*   **`dwarf_variables`**: Local variable live ranges keyed by `variable_id` (`INTEGER PRIMARY KEY`), with `function_id` (`INTEGER`, indexed), `name` (`TEXT`), `type_id` (`INTEGER`), `range_index` (`INTEGER`: `0`, `1`, `2` for multi-range `.debug_loc` splits), `start_address` (`INTEGER`), `end_address` (`INTEGER`), `first_use_offset` (`INTEGER`: `start_address - function.address`), `storage_kind` (`TEXT`: `stack`, `register`, `constant`), `reg_name` (`TEXT`, nullable), `stack_offset` (`INTEGER`, nullable; normalized to entry-PC `RSP` via `DW_AT_frame_base`), and `const_value` (`INTEGER`, nullable).
*   **`dwarf_inlines`**: Inlined call-site ranges keyed by `inline_id` (`INTEGER PRIMARY KEY`), with `caller_function_id` (`INTEGER`, indexed), `callee_function_id` (`INTEGER`, nullable), `callee_name` (`TEXT`), `start_address` (`INTEGER`, indexed), `end_address` (`INTEGER`), `call_file` (`TEXT`, nullable), and `call_line` (`INTEGER`, nullable).
*   **Cross-table join contract with decompiler tables**: `dwarf_functions` joins to decompiler-extracted `functions` and `symbols` primarily on integer `address` (`WHERE dwarf_functions.address = functions.address AND dwarf_functions.is_declaration = 0`), breaking identical-code-folding (ICF) or constructor-alias (`D1Ev`/`D2Ev`) ties by matching `dwarf_functions.linkage_name` against the raw mangled ELF symbol name in `symbols` (falling back to lowest `function_id` if no symbol matches).

### 3. Decompiler Adapter Contract (`Ghidra 12.2` Now, `IDA 9.5` Later)

*   **Low-RAM Ghidra `analyze` & Dot-Free `/var/tmp` Staging**:
    *   On `BinaryArch.ELF64` (`attila_linux_64`), `twdll._ghidra` will disable the `"DWARF"` option in Ghidra's `"Analyzers"` property list inside an open program transaction before running headless analysis.
    *   Because `twdll` is pre-release, `.meta.json` uses no `schema_version` fields or version-bump migrations (re-analysis is triggered explicitly via `twdll clean analyze`).
    *   Because Ghidra's project locator rejects paths containing a leading-dot segment (`.twdll` or `.cache`) and Linux `/tmp` is typically an in-memory `tmpfs` (consuming up to 4 GiB of physical RAM on an 8 GiB host), `twdll._ghidra` will centralize temporary project staging using `tempfile.TemporaryDirectory(prefix="twdll_ghidra_", dir=...)` with `dir=Path("/var/tmp")` on `HostOS.LINUX` (when `/var/tmp` exists as a directory) and `dir=None` on `HostOS.WINDOWS`.
*   **Extract-Time Pass-Scoped Batch Population in `twdll._ghidra`**:
    *   Instead of per-function closure queries and per-function decompiler cache flushes (or loading all 10 `dwarf_*` tables into a single in-memory Python container), `twdll._ghidra` will stream four pass-scoped SQLite queries from `twdll.database` into the temp-staged program database across **four coarse transactions**, clearing Ghidra's undo history after each transaction so neither Python row objects nor Ghidra undo state accumulate in memory:
        1. **Pass 1 (Primitives, Enums, Typedefs, and Sized Struct/Union Shells)**: Stream `dwarf_types` and `dwarf_enumerators` to create enum definitions, typedefs, and empty sized struct/union shells (`byte_size >= 1`, falling back to `1` byte when `byte_size` is `NULL` or `0`) for all composite types. Types with `is_stl_stub = 1`, `is_declaration = 1`, or `is_referenced = 0` remain lightweight empty sized shells.
        2. **Pass 2 (Synthesized `<Class>_vtbl` Structs & Pre-Flattened Referenced Struct Members)**: Stream `dwarf_vtable_entries` to populate `<Class>_vtbl` structs with function-pointer slots at `slot_index * 8` (stamping `<Class>_vtbl` at `vtable_address` in `.rodata` / `.data.rel.ro` after clearing existing undefined/pointer listing units at that range). Then stream `dwarf_members` (`WHERE is_layout_conflict = 0`) and `dwarf_inheritance` (`WHERE is_virtual = 0 AND is_empty_base = 0 AND has_tail_padding_overlap = 0`) for referenced non-stubbed types (`is_referenced = 1 AND is_stl_stub = 0 AND is_declaration = 0`), typing `_vptr$...` members at offset `0` as `<Class>_vtbl *` (and inherited secondary base vptrs via their base class's `<Base>_vtbl *`).
        3. **Pass 3 (Custom-Storage Function Signatures)**: Stream concrete `dwarf_functions` (`WHERE address IS NOT NULL AND is_declaration = 0`) and their `dwarf_parameters`, applying each matched function's signature under the default System V x86-64 calling convention (never `"__thiscall"`) with explicit custom parameter and return storage:
            *   When `is_sret = 1`: parameter 0 is `__return_storage_ptr__` (`ReturnType *`) pinned to `RDI`, followed by `dwarf_parameters` (with `this` at parameter 1 on member functions—or first user parameter on free functions—pinned to `RSI`, and remaining parameters pinned to their entry-PC `reg_name` or entry-`RSP` `stack_offset`), and return storage pinned to `RAX` (`ReturnType *`).
            *   When `is_sret = 0`: parameters from `dwarf_parameters` (including explicit `this` at ordinal 0 pinned to `RDI`) are bound directly to their entry-PC register or entry-`RSP` stack storage (assigning standard System V ABI fallback register/stack slots for `-O2` parameters with `storage_kind = 'none'`), and return storage is bound to `VOID_STORAGE` (`void`), `XMM0` (`float`/`double`), or `RAX` (`<= 8`-byte integer/pointer/struct; `RAX:RDX` join storage for `9..16`-byte trivial structs).
        4. **Pass 4 (Locals & Inlined Subroutine Pre-Comments)**: Stream `dwarf_variables` (`WHERE storage_kind IN ('stack', 'register')`) to add non-conflicting stack locals (skipping offsets that overlap parameters or earlier stack locals) and multi-range register locals (with `first_use_offset > 0` and split names `name`, `name$1`, `name$2` merged by Ghidra's local symbol map), and stream `dwarf_inlines` grouped by `start_address` to attach concatenated pre-comments (`// inline <callee_name> @ <call_file>:<call_line>`) at each inline range entry address.
    *   After Pass 4 and clearing undo history, `twdll._ghidra` will open the decompiler interface once (with pre-comments enabled by default) and run decompilation without mid-loop cache flushes. The scope of bulk C++ pseudocode extraction across all functions vs. filtered game namespaces is gated on the Step 3A empirical throughput benchmark ([SPEC.md §6.3](../../SPEC.md#L229-L235)).
*   **IDA 9.5 Compatibility Contract**:
    *   Because all type deduplication, EBO/tail-padding flattening, vtable slot mapping, and `sret` register classification are materialized in the backend-neutral `dwarf_*` SQLite tables using plain integer addresses and `image_base`, a future IDA 9.5 adapter can consume the exact same SQLite tables without Ghidra dependencies.

## Success Metrics & Risks

*   **Acceptance Criteria**:
    *   `twdll-dwarf` extracts and deduplicates all 469 CUs (`23,553,961` DIEs) of `attila_linux_64` into `.twdll/extract/ghidra_attila_linux_64.sqlite.staging` in under 60s and under 3.2 GiB peak RSS on an 8 GiB host.
    *   `twdll analyze` on `attila_linux_64` with `Analyzers.DWARF = false` and `/var/tmp` staging completes within default JVM heap limits on an 8 GiB host without `OutOfMemoryError`.
    *   Pass-scoped batch population + `DecompInterface` on sampled `attila_linux_64` C++ methods (including polymorphic classes with `_ZTV` vtables, EBO/tail-padding inheritance, `<= 16`-byte non-trivial `sret` return types like `std::unique_ptr` and `CA::Pixel8888`, and classes with `std::vector` / `std::string` members) emits typed `this->field_name`, `this->_vptr->virtual_method(...)`, and unshifted parameter lists within `< 4.5 GiB` combined JVM + `decompile` peak RSS.
    *   `twdll sql` queries `attila_linux_64.dwarf_*` tables and joins `attila_linux_64.dwarf_functions` with `attila_linux_64.functions` and `attila_linux_64.symbols` in a single read-only session.
*   **Key Risks & Mitigations**:
    *   *Clang 3.4.2 vs. GCC 4.8.x DWARF dialect differences in `attila_linux_64`*: Handle both `DW_AT_MIPS_linkage_name` (Clang) and `DW_AT_linkage_name` (GCC), read `DW_AT_object_pointer` from either the declaration or definition DIE, inherit missing formal parameters across `DW_AT_specification` (`2,268` methods), and link Clang's `10,314` `DW_AT_declaration` class stubs to their full definitions across CUs by qualified name.
    *   *JVM heap growth during upfront struct population*: Stream rows per pass from SQLite (releasing Python lists between passes), stub internal STL/compiler template namespaces (`is_stl_stub = 1`), populate full struct members in Pass 2 only for referenced types (`is_referenced = 1`), and call `program.clearUndo()` after each of the four coarse transactions.
    *   *Linux `/tmp` `tmpfs` exhaustion when staging `.rep/` directories*: Stage temporary Ghidra project directories under `/var/tmp` on Linux (outside `/tmp` `tmpfs` and free of leading-dot path segments) so `.rep/` file staging does not consume `tmpfs` RAM.

## Alternatives Considered

### Alternative A: Tuning or Forking Ghidra 12.2's Built-in Java `DWARFAnalyzer`

*   **Pros**: Runs inside Ghidra's existing analysis pipeline without an external Rust extractor.
*   **Cons**: Verified in Ghidra 12.2 source that `DIEContainer.indexData()` unconditionally indexes all `23,553,961` DIEs in JVM heap before consulting `DWARFImportOptions`. Fixing its five C++ defects (unimplemented `DW_AT_vtable_elem_location`, `__thiscall` deletion of `this` on x86-64, broken `sret` `autoParams`, EBO/tail-padding drops, and `entryPc`-only `.debug_loc` lookups) would require maintaining a custom Java/Gradle fork of Ghidra's internal `Base.jar` and would still lock DWARF data inside `.gpr` instead of backend-neutral SQLite.
*   **Reason for Rejection**: High JVM RAM usage, high maintenance cost across Ghidra releases, and incompatible with backend-neutral SQLite and IDA 9.5 reuse.

### Alternative B: Black-Box `ddbug_parser v0.6.0` Without Direct `gimli` Traversal

*   **Pros**: Higher-level Rust wrapper around `gimli` with prebuilt `Unit`, `Type`, and `Function` structs (benchmarked on raw traversal of `attila_linux_64` at 26.56s and 2.88 GiB peak RSS).
*   **Cons**: Verified in `ddbug_parser-0.6.0/src/dwarf.rs` that `File.debug_info` and DIE offsets are private (`pub(crate)`), and `ddbug_parser` drops `DW_AT_virtuality`, `DW_AT_vtable_elem_location` (`95,354` vtable slots), `DW_AT_containing_type`, `DW_AT_artificial`, `DW_AT_object_pointer`, virtual-base `DW_AT_virtuality` (silently misparsing `791` virtual-base `exprloc` offsets as bit offset `0`), and `DW_AT_specification` parameter inheritance (`2,268` out-of-line methods).
*   **Reason for Rejection**: Cannot extract the C++ vtable, inheritance, and `this`/`sret` metadata needed to fix Ghidra's C++ pseudocode; using `gimli v0.34.0` + `object v0.40.0` directly provides full DIE attribute access within the `< 60s / < 3.2 GiB` extraction budget.

### Alternative C: Pure-Python DWARF Extraction via `pyelftools` or Text-Parsing `llvm-dwarfdump`

*   **Pros**: Avoids compiling a Rust binary in `tools/twdll-dwarf/`.
*   **Cons**: `pyelftools 0.33` took 53.66s and 3.56 GiB peak RSS for just 10 of 469 CUs (~41.2 minutes projected for `attila_linux_64`). `llvm-dwarfdump` DIE dumps output unstructured indented text with no machine-readable format for full DIE trees.
*   **Reason for Rejection**: Too slow (`pyelftools`) or unstructured (`llvm-dwarfdump` text output) for full 469-CU extraction; `llvm-dwarfdump --statistics` is retained strictly for developer verification in tests/benchmarks.

### Alternative D: Per-Function Type Closure Injection & Per-Function `DecompInterface.flushCache()`

*   **Pros**: Injects only the types directly referenced by a single function prior to calling `decompileFunction()`.
*   **Cons**: Calling `DecompInterface.flushCache()` on every function purges the native C++ `decompile` worker process's symbol and type cache tens of thousands of times, leaves callee function signatures and virtual method targets untyped when decompiling a caller, and risks order-dependent stub-vs-struct overwrites in Ghidra's shared `DataTypeManager`.
*   **Reason for Rejection**: Pass-scoped batch population of deduplicated types, vtables, and function signatures at the start of `twdll extract` (with undo history cleared between transactions) gives `DecompInterface` full caller, callee, and vtable visibility with zero `flushCache()` loops.

### Alternative E: Separate `.twdll/extract/dwarf_attila_linux_64.sqlite` Database File

*   **Pros**: Keeps DWARF tables in a separate physical SQLite file from decompiler-extracted tables.
*   **Cons**: Breaks the 1-to-1 `.twdll/extract/<decompiler>_<binary>.sqlite` layout in [SPEC.md §2](../../SPEC.md#L62-L67) and breaks `twdll sql` ([SPEC.md §6.4](../../SPEC.md#L241-L245)), which attaches only `<decompiler>_<binary>.sqlite` files under `<binary>` schema aliases.
*   **Reason for Rejection**: Violates the single-database-per-binary contract and `twdll sql` schema-attachment model.

    *   ICF / alias tie-breaking: Match `dwarf_functions.linkage_name` against `sym_table.getSymbols(addr)`.
    *   Register tables: `SUBREG_MAP` (1/2/4-byte sub-registers for all 16 GPRs `RAX`..`R15` plus `XMM0..15` `_Da`/`_Qa`), `REG_ROOTS` (mapping sub-registers to 64-bit roots and `YMM{i}` to `XMM{i}`), `INT_FALLBACK_REGS = ("RDI", "RSI", "RDX", "RCX", "R8", "R9")`, `FLOAT_FALLBACK_REGS = ("XMM0".."XMM7")`.
    *   Return storage: `is_sret = True` -> prepend `__return_storage_ptr__` (`ret_ptr`) in `RDI`, mark `RDI` used and `int_fb_idx = 1`, return `ret_ptr` in `RAX`; `is_sret = False` -> `VOID_STORAGE` for `void`, `XMM0_Da`/`XMM0_Qa` (fallback `XMM0`) for `float`/`double`, `(RAX, RDX_sub)` join storage for `9 <= ret_sz <= 16`, else size-matched `RAX` sub-register.
    *   Parameter storage: Wrap by-value non-trivial `struct`/`class`/`union` params in an 8-byte pointer; deduplicate param names (`<name>_<ordinal>`); if `is_sret` and `ordinal == 0` and `reg_name == "RDI"`, shift to `"RSI"`; accept DWARF register only when `valid_abi_reg` holds (float -> `XMM0..7`, non-float -> `RDI..R9`) and `root not in used_reg_roots`, sizing to `pdt_len`; accept DWARF stack param only when `stack_offset >= 8` and disjoint from `used_stack_ranges`; fall back to next unused `FLOAT_FALLBACK_REGS` / `INT_FALLBACK_REGS` (assigning a 2-register `VariableStorage(program, reg1, reg2_sub)` pair when `not is_flt_param` and `9 <= pdt_len <= 16` and two GPR arg slots remain) else 8-byte-aligned stack slot from `next_fb_stack = 8`; commit via `java.util.ArrayList` and `FunctionUpdateType.CUSTOM_STORAGE`, `Function.DEFAULT_CALLING_CONVENTION_STRING`, `SourceType.IMPORTED`.
*   **Pass 4 (`_populate_locals_and_inline_comments`)**:
    *   Seed `used_names` with `{str(p.getName()) for p in gh_func.getParameters()}` so locals never collide with formal parameters; name split ranges `name` (`range_index == 0`) or `f"{name}${range_index}"`.
    *   Stack locals: Guard `off < 0 and off + sz <= 0` and disjoint from `used_stack`; create `LocalVariableImpl(vname, 0, vdt, VariableStorage(program, off, sz), program)`.
    *   **Register local entry-PC guard (Step 4 invariant)**: Skip any register local with `vr.first_use_offset <= 0` (prevents entry-PC register locals from evicting formal arguments); require `reg is not None and int(reg.getMinimumByteSize()) >= sz`; create `LocalVariableImpl(vname, int(vr.first_use_offset), vdt, VariableStorage(program, reg), program)`.
    *   Inline comments: Group by `start_address`, format `inline <callee_name>` (+ ` @ <call_file>:<call_line>` when both are present), deduplicate preserving order, and apply via `cu.setComment(CommentType.PRE, "\n".join(lines))`.
